# 给小程序签名

Kinter 把每个导入的包当「别人做的软件」。打开之前验三件事：包有没有被换过、是谁给的、该不该给人用。三件事对应三层东西——包签名、开发者证书、模型审查记录。

验不过就弹一句 iOS 用户都见过的提示：**未受验证的开发者，App暂时无法打开**，然后不启动。

## 为什么自签名等于没签

第一版做过「公钥跟着签名走 + 首次信任」：任何人都能自己生成一把 key、写个 `developerId` 叫 `com.apple.`，第一次点开时宿主只能问你要不要信。**问的那一刻，身份就已经是对方自己说的了。**

现在改成证书链：宿主里内置一把根公钥，只有拿根私钥签发的开发者证书才被认。自签名包不再提供「信任并打开」，直接挡——除非你手动打开「开发模式」。

伪造一个包，得同时拿到：根私钥（签证书）+ 开发者私钥（签包）+ 一模一样的包摘要。缺一样都过不去。

## 两层钥匙

| 钥匙 | 谁拿着 | 作用 |
|---|---|---|
| 根私钥 `root_ed25519.pem` | 你，离线保存 | 签发开发者证书。**只在签发时用到，永远不进 App、不进仓库** |
| 开发者私钥 `dev_ed25519.pem` | 开发者 | 签整包摘要。泄露只影响这一个开发者 |

宿主只内置根**公钥**（`PackageSignature.Anchor` 里一行 base64）。公钥能公开，伪造不了任何东西。

## 证书里绑死了什么

```json
{
  "kind": "kinter-developer-certificate",
  "version": 1,
  "rootKeyId": "root-1",
  "developerId": "com.example.dev",
  "publicKey": "…开发者公钥…",
  "packageDigest": "…整包摘要…",
  "issuedAt": "2026-11-07T12:55:53Z",
  "expiresAt": "2026-12-07T12:55:53Z",
  "review": { "model": "…", "verdict": "safe", "summary": "…", "findings": [] }
}
```

宿主验证书时逐条对：

- 证书签名是不是内置根签的
- 证书里的 `publicKey` / `developerId` 是不是和 `signature.json` 里的一致
- 证书里的 `packageDigest` 是不是等于**当场重算**的整包摘要（换包即失效）
- 有没有过期（默认 365 天，签发时可改）
- 模型审查结论就存在证书里，由根一起签，改一个字验签就失败

所以一张证书只对一个包有效，不能拿去签别的包，也不能把别人包的证书搬过来。

## 签发流程

`Tools/sign_app.py` 一条命令跑完：

1. 收集 manifest 与源码文本（HTML / JS / CSS / KTML / JSON，单文件 60 KB、总计 220 KB 封顶）
2. 送第三方模型审：偷隐私外传、编码外发、`eval` 远程加载、伪装系统界面、挖矿刷量、绕过安全模式、读别的小程序数据 → 判 `unsafe` 就退出，**不签证书、不签名**
3. 判 `safe` → 用根私钥签发证书（绑开发者、公钥、包摘要、审查结论、有效期）
4. 用开发者私钥签整包摘要
5. 两段内容 + 两段签名写进 `signature.json`

```bash
# 只做一次：生成根密钥（会打印根公钥 base64）
python3 Tools/sign_app.py --init-ca

# 日常签发
python3 Tools/sign_app.py ./my-app \
  --developer com.example.dev \
  --api-base https://api.example.com/v1 --api-key sk-xxx --model gpt-4o-mini \
  --ca-key ~/.kinter/ca/root_ed25519.pem
```

第一次没配接口会交互式问，存在 `~/.kinter/sign_config.json`（600 权限）。根私钥路径也可以走环境变量 `KINTER_CA_KEY`。

`--init-ca` 生成的根，必须把打印出来的公钥 base64 填进 `PackageSignature.Anchor.publicKeyBase64` 再重新构建 App——否则宿主不认这个根。本项目当前内置的根对应私钥在 `kinter-ca/root_ed25519.pem`（不在仓库里），记得离线备份。

## 宿主怎么判

| 情况 | 结果 |
|---|---|
| 证书链到内置根、摘要对、未过期 | 直接打开；审查结论写进 NSLog |
| 有签名、没证书（自签名） | 未受验证的开发者 → 挡住（开发模式除外） |
| 没 `signature.json` | 同上 |
| 证书不是内置根签的 / 证书签名不对 | 同上，正文说明「证书验签失败」 |
| 证书绑的包摘要对不上 | 同上，正文说明「包被换过」 |
| 证书过期 | 同上，「开发者证书已过期」 |
| 宿主自带示例、本机 AI 生成 | 直接打开（`isFirstParty`，本机产物） |

## 开发模式

设置 → 开发者签名 → **允许自签名（开发模式）**，默认关。

打开后，自签名包会弹「开发模式：未受验证的开发者」，可以点「信任并打开」，信任名单存本机（按 开发者标识 + 公钥 精确匹配，换一把 key 就得重信）。正式分发前把它关掉，否则这一层就形同虚设。

## 轮换根

根私钥泄露或要作废时：

1. `--init-ca` 生成新根，替换 `Anchor.publicKeyBase64`
2. 重新构建、分发 App
3. 用新根重签所有存量包（旧证书会全部失效，这是预期行为）

`Anchor` 目前是单个常量；要支持多根并存，把 `publicKeyBase64` 扩成 `[keyId: base64]` 字典即可，校验逻辑不用改。

## 边界

- 证书证明的是「这个包由持有根私钥的人授权、且没被改过」，不证明包本身在功能上安全——那是模型审查 + 宿主能力网关 + 安全模式三层的事。
- 模型审查看的是文本源码，看不了图片里藏的指令，也拦不住精心伪装的逻辑。它是签发前的门槛，不是运行时的保险。
- 根私钥在谁手里，谁就能发证书。它不该出现在 CI、仓库、聊天记录里。
